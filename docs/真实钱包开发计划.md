# 真实多链钱包开发计划

本文档用于冻结当前 Telegram Mini App 钱包产品的真实开发方向，替换现有 mock 流程，并作为后续实现、联调和上线的统一依据。

当前确认前提：

- 产品形态是 `Telegram Mini App`，但钱包本体按“类似 App 钱包”的思路设计
- 钱包是 `非托管` 模式
- 钱包前端不依赖 bot 后端处理助记词、私钥、密码、seed、签名材料
- 前期链支持：`TRON`、`BSC`、`ETH`
- 当前项目处于 `高保真 UI + mock 状态` 阶段，下一步要逐步替换为真实数据和真实状态

---

## 1. 产品边界

### 1.1 明确做什么

- 在 Telegram 内以 Mini App 形式运行的钱包前端
- 本地创建钱包
- 本地导入钱包
- 本地加密保存钱包金库
- 本地解锁钱包
- 直连链 RPC 读取多链余额和账户信息
- 后续支持真实签名和转账

### 1.2 明确不做什么

- 不托管用户助记词或私钥
- 不将明文助记词上传到服务端
- 不通过 bot 后端参与钱包解锁或签名
- 不使用 Telegram `cloudStorage` 存储任何钱包秘密
- 第一阶段不追求多账户、多地址簿、多签、硬件钱包等复杂能力

### 1.3 bot 后端的职责

bot 后端若存在，仅承担非敏感职责：

- Mini App 入口
- 菜单按钮
- 运营消息和通知
- 非敏感配置下发
- 埋点与非敏感日志

bot 后端不应承担：

- 助记词
- 私钥
- seed
- 密码
- 钱包加密解密
- 用户签名

## 2. 安全模型

### 2.1 为什么不用 Telegram cloudStorage 存秘密

原因不是“不能用”，而是“不应该用”：

- 它不是专门为密钥材料设计的安全存储系统
- 钱包秘密上云会扩大攻击面和责任边界
- 即使存的是密文，也会多出一份云端副本
- 云同步、账户迁移、版本兼容会让安全和运维更复杂

结论：

- 钱包秘密只存本地
- 密文尽量也只存本地

### 2.2 助记词和私钥的持久化原则

持久化允许存：

- 加密后的助记词
- vault 版本信息
- KDF 参数
- salt
- iv
- 链地址缓存和账户元数据

持久化禁止存：

- 明文助记词
- 明文私钥
- 明文 seed
- 用户密码

### 2.3 明文助记词只在内存存在是否合理

合理，而且这是 Web 钱包的正常路线之一。

准确说法应为：

- 持久化层不保存明文助记词
- 用户解锁时，助记词或 seed 临时进入内存，用于地址派生、签名等操作
- 锁屏、切后台、超时后，丢弃内存中的敏感会话

需要明确的现实边界：

- 在 `Web / Telegram WebView / JavaScript` 环境里，无法像原生安全模块那样强保证内存擦除
- 我们能做的是“尽量短驻留、尽量少暴露、不落盘、不打日志、不进 URL”

### 2.4 本地加密策略

建议方案：

- KDF：`Argon2id`
- 对称加密：`AES-GCM`
- 持久化容器：`IndexedDB`

不建议：

- 用 `sessionStorage` 保存钱包状态
- 用 `localStorage` 直接存敏感 vault 主数据
- 用自定义弱加密替代标准 KDF + AEAD

### 2.5 锁屏与会话策略

建议默认策略：

- 切后台立即锁定
- 前台无操作 `5` 分钟自动锁定
- 页面刷新后，如本地已有 vault，则进入“已锁定”而不是“欢迎页”

## 3. 多链架构

### 3.1 总体思路

采用“一套助记词 + 多链派生 + 多链适配层”架构。

链分组：

- `ETH / BSC` 归入 `EVM` 适配层
- `TRON` 单独适配

### 3.2 派生路径

建议默认单账户路径：

- ETH: `m/44'/60'/0'/0/0`
- BSC: `m/44'/60'/0'/0/0`
- TRON: `m/44'/195'/0'/0/0`

说明：

- ETH 和 BSC 可以共用 EVM 地址派生逻辑
- TRON 虽同样依赖 `secp256k1` 体系，但地址编码、交易结构、RPC 体系不同，必须单独处理

### 3.3 第一阶段功能范围

第一阶段只做：

- 单钱包
- 单账户
- 默认三条链地址派生
- 余额读取
- 基础账户信息读取

第一阶段暂不做：

- 多账户
- 多地址派生管理
- 代币添加/隐藏
- 复杂转账确认流
- 合约交互

## 4. 状态机与路由重构

### 4.1 当前问题

当前 [OnboardingMockContext.tsx](file:///Users/zhangandy/Documents/work/code/part2026/oldwang/wallet/wallet-poc-tgminiapp/src/pages/app/onboarding/OnboardingMockContext.tsx) 仍然是 mock 模型，不能继续作为真实钱包状态中心。

### 4.2 新的顶层状态

建议引入真实钱包顶层状态：

- `no_wallet`
- `locked`
- `unlocked`

含义：

- `no_wallet`：本地还没有 vault
- `locked`：本地已有 vault，但尚未解锁
- `unlocked`：vault 已解锁，可派生地址、读链、签名

### 4.3 路由建议

路由应逐步演进为：

- `/`：根据真实状态分发，而不是固定欢迎页
- `/onboarding/password`
- `/onboarding/mnemonic/generate`
- `/onboarding/mnemonic/backup`
- `/onboarding/mnemonic/verify`
- `/onboarding/import`
- `/unlock`
- `/home`

跳转原则：

- 无钱包 -> 欢迎页
- 有钱包未解锁 -> 解锁页
- 已解锁 -> 首页

## 5. 本地开发与调试

### 5.1 本地浏览器开发

用途：

- UI 开发
- 加密流程调试
- IndexedDB 调试
- 状态机和路由调试

命令：

```bash
pnpm install
pnpm dev
```

重点：

- 用浏览器开发工具查看 `IndexedDB`
- 检查锁定/解锁和刷新恢复逻辑
- 确保开发日志绝不输出助记词、私钥、密码

### 5.2 真实 Telegram 调试

开发到真实钱包阶段后，必须尽早在 Telegram WebView 中联调。

推荐做法：

1. 本地启动 Vite
2. 用 `cloudflared` 或 `ngrok` 暴露本地 HTTPS 地址
3. 将 bot 的 Mini App URL 指向该 HTTPS tunnel
4. 在 Telegram iOS / Android 客户端中真机调试

推荐命令示例：

```bash
pnpm dev
cloudflared tunnel --url http://localhost:5173
```

### 5.3 真机重点回归项

- 创建钱包后刷新是否仍能识别本地 vault
- 导入钱包后是否能进入已锁定/已解锁正确状态
- 切后台后是否立即锁定
- 输入法、软键盘和返回按钮行为是否正常
- Telegram iOS / Android WebView 差异

## 6. 部署与上线

### 6.1 环境建议

建议至少准备两套 bot 和域名：

- `staging bot`
- `production bot`

不要共用一个 bot 进行开发、联调和正式生产。

### 6.2 前端部署

前端可以部署到：

- Vercel
- Cloudflare Pages
- 自有 HTTPS 域名

上线前必须确认：

- `base` 配置正确
- 所有 `public/` 静态资源路径可用
- 域名和 Telegram Mini App URL 一致

### 6.3 上线前安全清单

- 错误监控不包含秘密字段
- 关闭所有敏感 debug 日志
- 锁屏逻辑稳定
- vault schema 有版本号
- 支持基础数据迁移

## 7. 推荐目录拆分

建议新增目录：

```text
src/
  wallet-core/
    crypto/
    vault/
    session/
    chains/
      evm/
      tron/
    mnemonic/
  state/
    wallet/
  pages/
    app/
      unlock/
```

职责建议：

- `wallet-core/crypto`：KDF、AES、随机数、字节处理
- `wallet-core/vault`：vault schema、创建、导入、加密、解密、持久化
- `wallet-core/session`：解锁态、锁屏、超时和后台清理
- `wallet-core/chains/evm`：ETH/BSC 地址派生、余额读取、签名
- `wallet-core/chains/tron`：TRON 地址派生、余额读取、签名
- `state/wallet`：面向页面层的全局状态

## 9. 当前推荐默认决策

除非后续明确反对，默认采用以下方案：

- 助记词标准：`BIP39`
- 账户模型：第一版 `单钱包 + 单账户`
- EVM 范围：`ETH + BSC`
- TRON 范围：第一版至少完成地址和余额读取
- 持久化：`IndexedDB`
- 加密：`Argon2id + AES-GCM`
- 会话：`切后台立即锁 + 前台 5 分钟自动锁`
